# Sidecar-side analyze supersession when completion arrives at dispatch

After ka-hexa landed Rust-side analyze cancellation (commits b3e1b54..6947b02), real-Zed metrics on ABTestArgumentResolver still show ~500-950 ms cold-start latency on the first completion after any typing pause. Investigation traced this to a structural limit of Rust-only cancellation.

The debouncer (server.rs:837-940) waits 300 ms + a 500 ms post-interactive quiet window, then fires didChange (Plain) + analyze (Supersedable). The writer task (bridge.rs:442-477) drains its mpsc channel into stdin in microseconds. By the time the user types the next character, the analyze bytes are already in the OS pipe (kernel buffer between Rust and JVM processes). Rust's cancel_pending (bridge.rs:823-828) only drops messages still in the in-process channel; it cannot recall bytes already crossed to stdin.

The signature is unambiguous: analyze_pending_cancelled_total = 0 across every post-ka-hexa session while sidecar_queue_wait consistently sits at 400-950 ms on the first completion after a pause. The sidecar dispatcher (AnalysisServer.kt:62-95) is single-threaded — it picks up the in-pipe analyze, spends 500-950 ms doing a full FIR pass, only then reads the queued completion from the pipe.

ka-hexa's cancellation window is the microseconds between "debouncer enqueues analyze on the bridge channel" and "writer task drains it." Effectively never in practice. The Rust-side approach has a structural ceiling; the fix must live in the sidecar.

## Approach

Mirror the ser-leba pattern. When the AnalysisServer dispatch loop pulls a completion request from the pipe, perform a Checkpoint-2-style lookahead drain on its inbound queue and:

(a) Skip any queued analyze for the same URI (or any URI) that appears alongside or before the completion. Same shape as ser-leba: respond with a superseded marker, do not invoke bridge.analyze. The Rust side already tolerates analyze responses arriving late; diagnostics will re-fire on the next debouncer cycle.

(b) Optionally defer an in-progress analyze at the next safe boundary. The Kotlin Analysis API is single-threaded and does not expose mid-KaSession interruption hooks; this can only be approximated by decomposing analyze into per-file passes that yield, or by accepting that an analyze already past the dispatcher checkpoint runs to completion (worst case ≈ one analyze duration of head-of-line blocking, but bounded).

Phase (a) is the high-value piece — it eliminates the "queued behind in-pipe analyze" case. Phase (b) is optional and may not be worth the complexity if (a) gets us to target.

## Settled decisions

- Where the check runs: AnalysisServer.handleRequest, mirroring ser-leba's Checkpoint 2. The lookahead-drain pattern already exists from ser-leba; extend it to recognize and short-circuit analyze entries.
- What "supersede an analyze" means: respond to the queued analyze request with the same shape it would normally return, so Rust does not see an error. The Rust debouncer re-fires analyze after the next post-interactive quiet window; diagnostics are delayed by one debounce cycle, not lost.
- Cross-bucket coordination: ser-leba uses per-URI buckets for completion. Analyze is also per-URI. The sidecar's local map extends to track latest-seen analyze seq per URI, and when a completion arrives at dispatch with a queued analyze for any URI, the analyze is marked stale.
- Metric to add: sidecar.metrics.counts.analyzeSupersededByCompletion, incremented when (a) fires. Same emission pattern as supersededAtDispatch.

## Acceptance criteria

- Real-Zed session shows sidecar_queue_wait p95 dropping below 200 ms for the first completion after a typing pause (log records that begin a new burst show queue_wait < 200 ms, not 500-950 ms).
- New counter analyzeSupersededByCompletion is emitted and > 0 on sessions where the cold-start pattern was historically present.
- analyze_pending_cancelled_total from Rust may stay at 0 (it's the wrong layer); the new sidecar counter is what to watch.
- Sidecar Kotest covering: (1) completion arrives with queued analyze for same URI → analyze superseded, completion dispatches without head-of-line wait. (2) Completion arrives with queued analyze for different URI → both proceed. (3) Multiple analyzes queued, single completion arrives → most recent analyze per URI kept, older ones superseded.
- Rust-side tests unchanged; no protocol change (additive sidecar response fields only, mirroring ser-leba).
- docs/lsp-protocol.md updated with cross-bucket dispatcher checkpoint behavior. Cross-link from architecture.md and ka-hexa.

## Out of scope

- Mid-KaSession interruption (still impossible without Analysis API checkpoint hooks).
- Multi-threaded sidecar dispatcher (Analysis API single-thread constraint).
- Per-bucket queue depth changes in the bridge channel.
- Decomposing analyze into yielding chunks (Phase b above — separate ticket if Phase a is insufficient).
- Removing ka-hexa's Rust-side cancel. Cheap fast-path even if rarely effective; keep as-is.
