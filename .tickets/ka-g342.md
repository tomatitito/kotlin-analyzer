# Add completion-burst sensor (sensors metrics run completion-burst)

The completion-latency sensor measures isolated single-completion timing inside the sidecar. It does not capture how Zed's typing-burst behavior interacts with the bridge queue, so it cannot validate the latest-wins fix from ka-rr3u or detect regressions in supersession behavior.

Add a 'completion-burst' sensor that drives the real Rust LSP server end-to-end (LSP -> bridge -> sidecar) with configurable bursts and reports the user-visible metrics that matter for typing latency. An ad-hoc Python driver was used during ka-rr3u validation to confirm a ~10-14x improvement on latest-completion latency. That driver was not committed; this ticket promotes the idea into a first-class sensor with its own output rendering.

## Implementation

- New Rust crate at `tools/sensors/` (package `kotlin-analyzer-sensors`, binary `sensors`).
- `clap` subcommand pattern so today the entrypoint is `cargo run -p kotlin-analyzer-sensors -- completion-burst`, and the eventual `sensors metrics run completion-burst` UX is the same binary under a thin wrapper.
- Drives the real kotlin-analyzer LSP binary over stdin/stdout (initialize, didOpen, rapid textDocument/completion bursts), the same path Zed uses.
- Promote the existing `LspTestClient` from `server/tests/integration_test.rs` into a small shared module (e.g. `kotlin-analyzer-server::lsp_client` or a `tools/sensors/src/lsp_client.rs` if extracting from server is awkward) so the sensor and integration tests share one LSP-client implementation.
- LSP binary discovery (in order): `--lsp-binary <path>` flag → `KA_BIN` env var → `target/release/kotlin-analyzer` (built with `cargo build --release -p kotlin-analyzer-server` if missing).
- No charts in v1. JSONL output is the long-term interchange format; if charts become useful later, a separate Python notebook or Rust `plotters`-based ticket can consume the JSONL.

## Sidecar-Ready Signal

After `initialize` + `initialized` + `didOpen`, the sensor sends a single warmup `textDocument/completion` request and waits for its response (any response, including empty `Ok(None)`, counts as ready). This is end-to-end deterministic — it proves the whole LSP→bridge→sidecar pipe works for the file under test before measurement starts. The warmup latency is recorded but excluded from aggregates. Stderr-grep ("sidecar ready") is **not** used.

## Configuration

CLI flags on the `completion-burst` subcommand:
- `--project-root <path>` (required; no default — see open-questions below)
- `--target-file <path>`, `--line <n>`, `--character <n>` (required)
- `--burst-size <N>` (default 5)
- `--burst-count <M>` (default 10)
- `--inter-request-gap-ms <ms>` (default 5)
- `--inter-burst-gap-ms <ms>` (default 2000)
- `--warmup-bursts <N>` (default 1; warmup bursts are run but excluded from aggregates)
- `--scenario <name>` (selects a named scenario; mutually exclusive with the per-burst flags above; see Default Scenarios)
- `--jsonl-output <path>` (write raw per-burst records as JSONL)
- `--regression-guard` (enable tight-burst invariant assertion on the tight-burst scenario; exit non-zero on violation)
- `--lsp-binary <path>`, `--max-startup-secs <n>`

## Default Scenarios

Available via `--scenario`:
- **tight-burst**: `--burst-size 5 --inter-request-gap-ms 5` — designed so requests queue faster than the writer drains. Used by `--regression-guard` to assert `superseded_before_send + superseded_in_flight == burst_size - 1`.
- **medium-burst**: `--burst-size 5 --inter-request-gap-ms 25` — mixed BeforeSend/InFlight; just measures, no assertion.
- **loose-burst**: `--burst-size 5 --inter-request-gap-ms 200` — no supersession expected; measures sequential latency for comparison with the completion-latency sensor.

A scenario is just a named preset for the CLI flags above. Users can also build their own ad-hoc scenarios via the raw flags.

## Output

Sensor-specific rendering, not the generic completion-latency table.

**Terminal table (per-scenario)**:
```
Scenario        N  bursts  latest_p50  latest_p95  bf_send  in_flight  sc_queue_p95  sc_compute_p95
tight-burst     5  10      105ms       162ms       0        40         103ms          51ms
loose-burst     5  10      48ms        72ms        0        0          0.1ms          45ms
```

**Per-burst record (JSONL, one object per measured burst)**:
- scenario name, burst index
- per-request: correlation_id, my_seq, sent_at_ms, recv_at_ms, latency_ms, outcome (`returned`/`superseded_before_send`/`superseded_in_flight`/`error`/`timeout`)
- latest-only request fields: latency_ms, sidecar_queue_wait_ms, sidecar_compute_ms (parsed from completion_metrics log lines)
- supersession totals delta for this burst: before_send, in_flight

**Aggregate report (stdout)**:
- For each scenario: bursts run, latest-only latency min/avg/p50/p95/max, supersession totals (BeforeSend / InFlight), sidecar_queue_wait p50/p95, sidecar_compute p50/p95.
- If `--regression-guard` is set and the tight-burst scenario violated the invariant, prints the violation and exits non-zero.

## Metrics Parsing

The sensor enables `completionMetrics` via `initializationOptions` and parses the LSP server's stderr for lines tagged `target=completion_metrics`. Fields extracted per request:
- `correlation_id`, `supersession_seq`
- `bridge_response_wait_ms`, `bridge_total_ms`, `rust_total_ms`
- `superseded_before_send_total`, `superseded_in_flight_total` (cumulative — sensor diffs across requests)
- `sidecar.stages.sidecar_queue_wait`, `sidecar.totalMs`

The current log format is the human-readable `tracing` default. The sensor uses a tolerant line-regex parser. If the `tracing-subscriber` JSON formatter is enabled (via env var `RUST_LOG_FORMAT=json` or similar) the sensor should prefer that; this can be a follow-up if not trivially supported today.

## Operating Modes

- **Default (metrics collector)**: runs the requested scenario(s), prints the table, writes JSONL if requested. Never exits non-zero on data — only on transport failures (LSP crash, timeout).
- **Regression guard (`--regression-guard`)**: same as default, plus asserts the tight-burst invariant (`superseded_before_send + superseded_in_flight == burst_size - 1` per measured burst). Exit non-zero on violation. Catches silent breakage of latest-wins (e.g. someone refactors `request_with_supersession` and uses the wrong bucket key, so supersession quietly stops working but no test fails).

## Acceptance Criteria

- New Rust crate at `tools/sensors/` builds via `cargo build` from the repo root and is included in `cargo test`/`cargo clippy` runs (or via its own pre-commit hook).
- `cargo run -p kotlin-analyzer-sensors -- completion-burst --help` lists the documented flags and scenarios.
- `cargo run -p kotlin-analyzer-sensors -- completion-burst --scenario tight-burst --project-root <p> --target-file <f> --line <n> --character <n>` produces a terminal report matching the documented table shape.
- `--jsonl-output <path>` writes one JSON object per measured burst with the per-burst fields listed above; output is valid JSONL (parseable line-by-line).
- The warmup completion is sent and awaited before measurement begins; warmup latency does not appear in aggregates.
- `LspTestClient` is shared between `server/tests/integration_test.rs` and the sensor (no duplicate implementation).
- `--regression-guard` exits non-zero when the tight-burst invariant is violated, and zero when it holds. A unit test simulates both outcomes (e.g. by stubbing the metrics parser).
- A short `docs/sensors.md` update mentions the new sensor and links to its `--help`. INDEX.md remains accurate.
- Manual validation against outfit-genie reproduces the ka-rr3u baseline numbers (latest-only latency in the ~100ms range under tight-burst), recorded in a closing note on this ticket.

## Open Questions Deferred to Implementation

- Whether to extract `LspTestClient` into the `kotlin-analyzer-server` crate (publishable module) or copy it into the sensors crate (avoids cross-crate exposure of test utilities). Implementer's call based on code volume.
- Exact tolerance window for the tight-burst invariant: with `--burst-size 5` we expect exactly 4 superseded. If timing flakiness becomes an issue in CI, soften to `>= burst_size - 1`. Default to strict equality and revisit if needed.
- JSON log format support — keep tolerant text parser for v1; add JSON-formatter support if it shortens the parser substantially.
