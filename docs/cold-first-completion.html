Cold First Completion — Why the First Keystroke After a Pause Is Slow

A different supersession problem than the one in the sibling page: not completion vs completion within a typing burst, but completion vs an already-in-flight background analyze across the OS pipe boundary. This is the page for ticket ka-p741.

See also: completion-pipeline.html · ticket ka-p741 (Phase a landed 2026-05-19) · ka-hexa (predecessor, Rust-side cancel) · ser-leba (structural template)

Status Fixed in ka-p741 Phase (a), landed 2026-05-19. This page now documents both the diagnosis (sections 1–4) and the implemented mechanism (sections 5–7).

1. The symptom

Type f after any typing pause → first completion took 500–950 ms. Continued typing within the same burst was fast (~30 ms warm). Pause, then start again with b → slow again.

Every typing burst has a slow first character and fast tail. The sibling page covered why warm-burst completions get superseded; this page covers why the cold first one stalls in the first place. Spoiler: it is waiting behind a background analyze request that crossed the OS pipe a few hundred milliseconds before the user pressed a key.

2. What's actually happening — the cold-start timeline

Two horizontal lanes (Rust LSP / JVM sidecar) cross over a vertical OS pipe at the moment requests change processes. The cancel window highlighted in red is when cancel_pending could have caught the analyze; it closes microseconds after step 4, hundreds of milliseconds before the user starts typing.

Note This is what used to happen. The diagnosis is unchanged — see Section 5 for the after-state diagram showing how the dispatcher now intervenes.

3. Why ka-hexa alone was insufficient

The Rust-side cancel only inspects the in-process mpsc channel. Once the writer task pulls a message and calls write_message, the bytes leave Rust's control.

The cancel mechanism's reach

Bridge::cancel_pending (server/src/bridge.rs:823-828) walks the mpsc::Sender<QueuedMessage> channel, marks anything matching the predicate as superseded, and returns. That channel is drained by the writer loop at bridge.rs:442-477 as fast as the kernel will accept bytes — typically a few microseconds for a JSON-RPC frame this size.

Once the analyze message leaves the channel and enters the OS pipe, there is no Rust-side handle on it. No file descriptor write can be retracted, no peek can identify which logical request the bytes belong to. The cancel path stays wired up — it just isn't enough on its own; the sidecar-side dispatcher check in Section 5 is what now does the load-bearing work.

4. Structural parallel with ser-leba

ser-leba solved an analogous problem one row up. It demonstrated that pushing the supersession check across the process boundary into the sidecar dispatcher works. ka-p741 generalises that pattern to cross request types, not just multiple requests of the same type.

Problem Stale completion bytes already in pipe by the time Rust knows a newer one exists Background analyze bytes already in pipe by the time the user types

The takeaway: this is the same shape of problem. ser-leba demonstrated the pattern works in production. ka-p741 is the same shape extended one axis.

5. The implemented fix — ka-p741 Phase (a)

Before — pre-ka-p741 cold start user-perceived: ~800–1000 ms
After — ka-p741 Phase (a) (landed) user-perceived: ~30 ms + protocol

Implementation — what actually landed

The dispatcher loop in sidecar/src/main/kotlin/dev/kouros/sidecar/AnalysisServer.kt was extended to track a separate "analyze:<uri>" bucket alongside the existing per-URI completion bucket, then to short-circuit any queued analyze whenever a completion is in the same dispatch window. The load-bearing functions:

  • hasCompletionInQueue(item) — scans the current dispatch window for a queued completion.
  • supersedeQueuedAnalyzes() — removes every queued analyze entry and short-circuits each one.
  • sendSyntheticAnalyzeResponse(request) — writes the no-op JSON-RPC result back to Rust.
  • analyzeSupersededByCompletionCount: an AtomicLong bumped once per short-circuit, emitted in the metrics block as analyzeSupersededByCompletion alongside the existing supersededAtDispatch.

The synthetic response is shaped to match what handleAnalyze would have emitted on a normal call, so the Rust side has nothing to special-case: 

{
  "diagnostics": [],
  "edits": [],
  "version": N           // echoed from the request when present
}

Ordering: analyze supersession runs before completion dispatch

The supersession check fires whether or not the completion that triggered it ultimately turns out to be stale itself: the queue gets flushed of analyzes either way, so a subsequent dispatch step can pick up the freshest completion without dragging a stale analyze in front of it.

Still out of scope (Phase b territory):

  • Mid-KaSession interruption. The Kotlin Analysis API is single-threaded and exposes no checkpoint hooks. If an analyze is already running (not merely queued in the pipe) when the completion arrives, it runs to completion. Worst-case latency stays bounded by one analyze duration.
  • Decomposing analyze into yielding chunks. Tracked as Phase b in the ticket; separable from Phase (a) and was not required to fix the lived symptom.

7. What this means for diagnostics

The log-signature of the fix, now observed in the post-ka-p741 session:

  • sidecar_queue_wait p50 dropped from 474 ms to 0.9 ms; p95 on first-of-burst records is now well under 200 ms.
  • analyzeSupersededByCompletion is > 0 (5 cumulative in the post-fix sample), scaling with the number of typing bursts. The counter is emitted on every metrics block in the same shape as supersededAtDispatch.
  • analyze_pending_cancelled_total stays at ~0, as predicted. It measures the Rust-side in-process channel, not the OS pipe; the new sidecar counter is the correct one to watch.
Caveat .sensors/log-analysis.py does not yet surface the new analyzeSupersededByCompletion field in its aggregate view (the per-session --path <file> summary also doesn't show it). The counter is present in the raw JSON record. A small script update is a worthwhile follow-up.

If analyze_pending_cancelled_total stays at 0 and analyzeSupersededByCompletion stays at 0 in a future session, the fix did not wire up. Seeing only the former at 0 is expected and not a regression.
