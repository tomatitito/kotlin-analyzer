Completion Pipeline & Supersession Checkpoints

Three checkpoints all answer the same question — "did a newer completion request arrive for this file before this one finished?" — but they fire at different points along the round trip between the Rust LSP and the JVM sidecar. This page explains why supersededAtDispatch is currently ~0.5× the volume of superseded_in_flight_total instead of the >5× we hoped for.

Why supersededAtDispatch / superseded_in_flight_total ≈ 0.5×

Checkpoint 2 only fires when the dispatcher sees multiple requests sitting in the pipe at the same time. The JVM processes each completion in ~140-180 ms. When typing is slower than that drain rate, requests arrive one-at-a-time — there is nothing to deduplicate and only Checkpoint 3 catches them, which means we have already wasted the CPU.

Walk through the burst below to see why: each time the JVM drains the pipe, it usually finds just a single request waiting (or none), so CP2's lookahead has nothing to throw away.

Typing burst walkthrough: f → fo → foo

Each card shows the OS pipe state (rectangle with slots) and what the JVM is doing. A filled slot is a request waiting to be picked up; a slot with a halo is the request currently being worked on by the JVM.

Cycle restarts. Reply 2 returns → CP3 fires again. Req 3 alone → CP2 silent.

CP2 only fires when typing is faster than the JVM can drain the pipe — i.e. when a second request for the same bucket lands before the dispatcher has had a chance to call read. In normal interactive typing (interval ~80-200 ms, JVM work ~140-180 ms), they alternate just fast enough for the JVM to keep up one-at-a-time, so the lookahead drain almost always picks up a single request. That is why supersededAtDispatch is small while superseded_in_flight_total stays high.
